Strategy search process

This document explains how strategy search produces card-balance evidence for each supplied kingdom. It describes what each stage does, not how the work is divided across computers.

Process overview

For each kingdom:

  1. Use Goldfish scoring to reduce every legal strategy to a 20,000-strategy reservoir.
  2. Use head-to-head games to build a matrix for the best 50 strategies.
  3. Search the reservoir for strategies that can beat the current equilibrium.
  4. Add confirmed responses to the matrix and repeat the search.
  5. Stop after two consecutive searches find no confirmed response.
  6. Save and validate the evidence for local balance analysis.
Optimization and parallelization

One campaign, one global CPU pool

  • Submit all 30 kingdoms together. The later 160-kingdom campaign uses the same design.
  • Put every independent piece of ready work into one global queue.
  • Do not reserve a fixed number of CPUs for a kingdom or a stage.
  • Give priority to small tasks that unlock the next scientific step, while spare CPUs continue bulk work.
  • Let each kingdom advance as soon as its own dependency is complete. Never wait for every kingdom to finish a stage.
Primary objective: minimize the time until all kingdoms finish. High CPU use matters because it serves that objective, not as a goal by itself.

The 400-CPU execution model

Parallelize scientific unitsCandidate scores, pair-and-seed games, and response games are independent. Those are the work units.
Keep only true barriersWait only when a ranking, equilibrium, or statistical decision needs all evidence from the current step.
Hide barriers across kingdomsWhen one kingdom reduces results or solves an equilibrium, run simulations for other kingdoms.

Recommended worker shape

Treat one CPU core as one simulation lane. A practical starting shape is 100 four-core containers, each running four independent native simulation lanes. This uses all 400 cores without relying on one simulation job to scale across several threads.

That container shape is not a scientific rule. Before production, benchmark one, two, four, and eight cores per container on the same work. Choose the shape with the highest completed games per billed CPU-second, provided it can still fill all 400 cores. If four independent lanes in one container interfere with each other, use smaller containers.

Keep the pool useful

  • Build and deploy one image per software version before campaign timing starts.
  • Initialize the native simulation engine when a container starts, then reuse it for many work chunks.
  • Keep containers warm between adjacent Goldfish, matrix, and PSRO bursts instead of rebuilding the pool for each stage.
  • Size chunks from measured throughput. Increase chunk size until startup, dispatch, and result overhead are a small part of wall time; keep enough chunks to fill at least 400 cores.
  • Use completion-order scheduling: assign the next ready chunk as soon as any lane becomes free.

1. Build the Goldfish reservoir

Approved conceptual process

Goldfish scoring is a fast first filter. It measures each strategy against three movement profiles: stationary, chaser, and kiter. It does not measure how well the strategy performs against the other strategies.

  1. Generate and score all 12,972,960 legal strategies with the first fixed shuffle seed against all three movement profiles.
  2. Take the best 500,000 unique strategies and save them with their results.
  3. Score each of the saved 500,000 strategies with three more fixed shuffle seeds against the same movement profiles.
  4. Combine the results from all four shuffle seeds.
  5. Take the best 20,000 unique strategies and save them with their results as the reservoir.

The reservoir is the candidate set for the competitive search. A high Goldfish rank does not prove that a strategy is competitively strong. The later stages test that through head-to-head games.

Optimization and parallelization

Stage 1: all strategies to 500,000

  1. Divide each kingdom's ordered strategy positions into independent ranges.
  2. Generate strategies inside the worker that scores them. Do not create or transfer strategy JSON before scoring.
  3. Run one scoring lane per CPU core. Score a batch in memory across all three movement profiles.
  4. Keep only the range's best 500,000 candidates in a compact sorted stream. Never save per-game or repeated full-strategy data.
  5. Store that stream temporarily only because it is too large for a routine function result.
  6. Perform one exact multiway merge to select the global best 500,000 unique strategies.
  7. Write the final top-500,000 file once, validate it, then delete the temporary streams.

Stage 2: 500,000 to 20,000

  1. Split the 500,000 retained positions into independent candidate-and-seed ranges.
  2. Score the three new seeds in parallel across the global pool.
  3. Combine each candidate's four-seed result once.
  4. Keep only each range's best 20,000 candidates in a compact temporary stream.
  5. Merge only the candidates that can still enter the global top 20,000.
  6. Write the final reservoir once, validate it, then delete the temporary streams.

How to use 400 CPUs

  • For 30 kingdoms, make ranges large enough to amortize overhead but keep at least several hundred ranges ready across the campaign.
  • Do not force 400 tiny files from one kingdom when ranges from 30 kingdoms already fill the pool.
  • Start a kingdom's stage 2 as soon as its top 500,000 merge finishes, even while other kingdoms remain in stage 1.
  • Run each kingdom's merge as soon as its final range arrives. Continue scoring other kingdoms during the merge.
Measure: candidates per CPU-second; profile trials per CPU-second; container startup; queue delay; bytes written per candidate; merge read time; merge CPU time; final file write time; and useful CPU occupancy over the whole campaign.

2. Build the initial game matrix

Approved conceptual process

A game matrix records how each selected strategy performs against every other selected strategy.

  1. Take the top 50 strategies from the reservoir.
  2. Play every pair of strategies, including each strategy against itself.
  3. For each pair, use 125 fixed shuffle seeds. Play twice per seed so that each strategy goes first once.
  4. Record the results and gameplay evidence for each pairing.
  5. Use the first 75 seeds to calculate the initial equilibrium.
  6. Keep seeds 76–100 as a depth check and seeds 101–125 as independent evidence for later analysis.

The equilibrium is a weighted lottery over strategies. Its weights describe how often each strategy should be selected when no strategy in the current matrix has an advantage over the lottery.

Optimization and parallelization

Parallel unit: pair × seed range

  1. Represent the matrix as 1,275 independent strategy pairs, including 50 self-play pairs.
  2. Split each pair's 125 seeds into work chunks large enough to amortize dispatch.
  3. Run both first-player orders together so each chunk returns a balanced result.
  4. Send all ready chunks from all kingdoms to the global pool.
  5. Return compact integer totals and required gameplay evidence, not one record per game.
  6. Combine chunks by pair and seed order with deterministic integer addition.
  7. Solve the equilibrium after the first 75 seeds for every required pair are complete.
Key point: there is no reason to run an entire kingdom's matrix inside one container. The games are independent until the equilibrium solve.

Barrier and critical path

The matrix has one true barrier: the initial equilibrium cannot be solved until the required 75-seed results are complete. Seeds 76–125 can run at the same time, but they must not delay the equilibrium if the scientific process does not require them for PSRO.

The equilibrium solve is small and sequential. Give it immediate priority, then release that kingdom's first PSRO screen. Other CPUs continue matrix or Goldfish games for other kingdoms.

Measure: games per CPU-second; chunk dispatch overhead; pair aggregation time; equilibrium solve time; time from the last required game to PSRO release; and CPU use while each kingdom crosses the barrier.

3. Search for responses with PSRO

Approved conceptual process

Policy-space response oracles (PSRO) repeatedly search for strategies that can beat the current equilibrium. A response is a reservoir strategy that appears to beat the equilibrium by more than the 51% threshold.

Each search follows three steps: screening, confirmation, and admission.

Optimization and parallelization

Adaptive global work

  • Freeze the current equilibrium for one look.
  • Create work only for candidates and seed ranges needed at that look.
  • Run those games across all free CPU lanes.
  • Reduce candidate results and make the scientific decision.
  • Create the next look only for unresolved candidates.

This preserves the approved adaptive process and avoids paying for deeper evidence that rejected or confirmed candidates do not need.

Approved conceptual process: screen

Screen the reservoir

  1. Exclude strategies that are already in the matrix.
  2. Play every remaining reservoir strategy against the current equilibrium.
  3. Start with 8 shuffle seeds and increase the evidence through 16, 32, 64, 128, 256, and 512 seeds when the result is still uncertain.
  4. Reject a strategy when the evidence shows that it does not exceed the 51% threshold.
  5. Send a strategy to confirmation when the evidence shows that it exceeds the threshold.
  6. Mark a strategy as unresolved when the maximum screening evidence is not enough to make either decision.

Each shuffle seed produces two games with opposite first players. The search follows the equilibrium weights as closely as the available number of games allows.

Optimization and parallelization: screen
  1. At each depth, split active candidates into chunks and distribute them globally.
  2. Within each candidate, split large seed work only when needed to expose enough parallelism.
  3. Keep the opponent schedule fixed and send its compact representation once per worker, not once per game.
  4. Aggregate scores by candidate with exact integer counts.
  5. Make all decisions for that depth in one pass, then immediately release the next-depth work.
Available parallelism: the first look has nearly 20,000 candidates per kingdom. Thirty kingdoms provide almost 600,000 candidate evaluations before any deeper look.
Approved conceptual process: confirm

Confirm possible responses

  1. Test every possible response again with fresh shuffle seeds.
  2. Increase confirmation evidence through 400, 800, 1,600, 3,200, and 6,400 seeds when needed. (when needed to get 95% CI above 51%?)
  3. Account for the number of possible responses being tested in the same search. (what is this? statistical thing to account for false positives given testing a lot of items?)
  4. Confirm only strategies whose adjusted evidence remains above the 51% threshold.
  5. Leave strategies unresolved when the maximum confirmation evidence is not enough to confirm them.

Fresh confirmation prevents screening results from also serving as final proof.

Optimization and parallelization: confirm
  1. Use separate fresh-seed tasks; do not mix screening and confirmation evidence.
  2. Parallelize candidate × seed-range work exactly as in screening.
  3. Schedule only the additional seeds needed to reach the next cumulative look.
  4. Reduce all provisional candidates before applying the across-candidate statistical adjustment.
  5. Stop scheduling a candidate as soon as the scientific rule reaches a terminal decision.
Scientific boundary: the confidence rule and multiple-testing adjustment are not optimization choices. They must be answered and fixed separately. Parallel execution must produce the same candidate decisions as serial execution.
Approved conceptual process: admit

Admit a confirmed response

  1. Order confirmed responses by confidence lower bound, mean score, confidence upper bound, Goldfish rank, and deterministic strategy identity.
  2. Admit the strongest response to the matrix.
  3. Play the admitted strategy against every strategy already in the matrix.
  4. Add the new results as a row and column in the matrix.
  5. Calculate a new equilibrium from the expanded matrix.
  6. Retest the other confirmed responses against the new equilibrium.
  7. Run another full reservoir search after the confirmed queue is empty.

Only one response is admitted at a time because each admission can change the equilibrium and make other responses irrelevant.

Optimization and parallelization: admit
  1. Keep the admission order serial because the next equilibrium depends on the chosen response.
  2. Parallelize the new matrix row by existing opponent × seed range.
  3. Run the equilibrium solve immediately when the row is complete.
  4. Parallelize retesting of the remaining confirmed queue against the new equilibrium.
  5. Reuse only scientific evidence that remains valid for the new equilibrium; never reuse an old response score as if the opponent lottery had not changed.

The admission decision is sequential. The thousands of games around it are not.

Approved conceptual process: stop

Stop after two clean searches

A search is clean when it finds no confirmed response.

  1. Count the first clean search.
  2. Search the same reservoir again against the same matrix and equilibrium.
  3. Finish when the second consecutive search is also clean.
  4. Reset the clean-search count whenever a response is admitted.

Two clean searches are evidence that the saved 20,000-strategy reservoir contains no response that this process can confirm against the final equilibrium. They do not prove that no response exists outside the reservoir or that the game has only one equilibrium.

An interrupted or inconclusive search is incomplete. A time limit, failed task, or manual stop must not count as a clean search.

Optimization and parallelization: stop

This is a decision inside PSRO, not a separate compute stage.

  • Begin the second clean search as soon as the first clean search validates.
  • Use the same parallel screen and confirmation machinery.
  • Record the stopping decision after all required evidence is complete.
  • Do not add delay, shutdown margins, or separate compute allocation for stopping.
Measure: games per CPU-second at every look; surviving candidates by depth; dispatch and reduction time per barrier; equilibrium-solve delay; matrix-row refill time; idle CPU-seconds while a kingdom waits; and total PSRO critical-path time.

Save and validate the evidence

Approved conceptual process

When done, save enough evidence to reproduce and inspect every scientific decision:

  • the top 500,000 Goldfish results;
  • the final 20,000-strategy reservoir;
  • all game-matrix results;
  • the equilibrium after each matrix change;
  • screening and confirmation games, seeds, scores, and decisions;
  • admitted responses;
  • the final stopping result;
  • gameplay evidence used for card-balance analysis.

Validate these files before the campaign is complete. Download the validated evidence, then produce balance reports and comparisons locally. Reporting does not change the strategy search or its completion result.

Optimization and parallelization

Save decisions, not task mechanics

  • Return small worker results directly as compact numeric data. Do not create a file for every Matrix or PSRO task.
  • Never save one record per game. Save the exact aggregate evidence needed to reproduce each scientific decision.
  • Use temporary files only for large Goldfish streams that do not fit comfortably in a function result.
  • Save one compact kingdom checkpoint at each scientific barrier: top 500,000, top 20,000, completed Matrix, completed PSRO look, admission, and final stop.
  • Write each final scientific artifact once. Validate it immediately, then delete its temporary inputs.
  • Download only final scientific evidence. Download completed kingdoms concurrently, capped at measured network throughput.
Minimal storage model: ephemeral worker result → compact scientific checkpoint → final validated evidence. If a worker result is lost before the next checkpoint, rerun that small task instead of making every task durable.
