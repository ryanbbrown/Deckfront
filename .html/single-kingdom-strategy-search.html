Single-kingdom strategy search

Each step below has three sections: the process, a plain language description, and the implementation detail. Open a section to read it.

1. Build the Goldfish reservoir

The process in five steps
  1. Play all 12,972,960 strategies with shuffle number 1 against all three dummy opponents. That is three games per strategy.
  2. Rank them. Keep the best 500,000. The rank rewards, in order: wins against the weakest dummy opponent, wins in total, fewer turns to win, more damage early, and more money spent.
  3. Play those 500,000 strategies with shuffle numbers 2, 3, and 4 against all three dummy opponents. That is nine more games per strategy.
  4. Add up each strategy's numbers from all four shuffles.
  5. Rank them again with the same rules. Keep the best 20,000. That is the reservoir.
Plain language description

This step takes every legal strategy for one kingdom and keeps the 20,000 that play best on their own. That set is called the reservoir. Later steps play those 20,000 strategies against each other.

A strategy is a shopping list: five cards to buy, in order, each with a target count. There are 12,972,960 possible shopping lists for a kingdom.

A Goldfish game is a solo game. The strategy plays against a dummy opponent that never attacks back. We test each strategy against three dummy opponents: one that stays still, one that walks toward the strategy, and one that walks away. The strategy wins when it deals 50 damage. The game stops after 30 turns.

Every game uses a fixed deck shuffle. A shuffle number chooses the shuffle. The same strategy with the same shuffle number always plays the exact same game, so every result can be checked again later.

How we rank strategies

Each strategy gets five numbers per dummy opponent from its games:

  1. Games played.
  2. Games where it reached 50 damage.
  3. Turns it took to reach 50 damage. An unfinished game counts as 31 turns.
  4. Damage total across all 30 turns. This rewards early damage.
  5. Money spent.

To compare two strategies, look at these things in this order. The first difference decides.

  1. More wins against its weakest dummy opponent.
  2. More wins in total.
  3. Fewer turns against its slowest dummy opponent.
  4. Fewer turns in total.
  5. More damage total against its weakest dummy opponent.
  6. More damage total in total.
  7. More money spent.
  8. Lower strategy number.

The last rule means no two strategies ever tie.

Implementation detail

Strategy numbers instead of strategy lists

We never write down all 12,972,960 shopping lists. Instead, each strategy has a number from 0 to 12,972,959. The Rust program can turn any number into its shopping list in a few nanoseconds, and the same number always gives the same list. Every file stores the number, not the list.

Each number gives a different list. So there are no duplicates to remove.

Fixed settings

The kingdom, the four shuffle numbers, the 30-turn limit, and the 200-action safety limit per turn are the same for the whole run. Each cloud computer loads them once at start.

Result rows and result files

Every result is one row of exactly 64 bytes: the strategy number (4 bytes), then the 15 result numbers (three dummy opponents × five numbers, 4 bytes each). Rows are written straight into a file, one after another, with no text and no formatting. A file of one million results is 64 MB. Reading or writing it is a single pass with no parsing.

Each file starts with a short header: which range of strategy numbers it covers, how many rows it has, and a checksum. The checksum is a number computed from every byte of the rows. A reader computes it again and compares. If the file was cut short or damaged, the two numbers differ and the reader rejects the file.

Step 1: play every strategy with shuffle 1

  1. The Python script splits 0 to 12,972,959 into numbered ranges of equal size. It picks the size so one range takes a few minutes on a 4-core computer.
  2. Each cloud computer receives one range: a start number and an end number.
  3. The Rust program splits the range across its 4 cores. Each core takes a number, builds the shopping list, plays three games, writes one 64-byte row, and moves to the next number. It keeps nothing else in memory.
  4. Each computer appends its rows to its own file as it goes, in strategy-number order. There is no shared file, so computers never wait for each other. When the range is done, the computer fills in the header and the file is complete.
  5. If a range fails, only that range runs again. Its result is identical because nothing is random.

Step 2: keep the best 500,000

  1. One computer with more memory runs the Rust program in reduce mode. It has to be one computer because the best-500,000 list must see every row.
  2. It reads every range file once, in order. It checks each file's checksum and checks that the ranges cover every strategy number exactly once. That is about 830 MB of reading, and the reading is the slow part.
  3. It keeps a running list of the best 500,000 rows. Each new row is compared to the current worst row on the list. Most rows lose and are dropped after that one compare. The list needs about 32 MB of memory.
  4. It writes top-500000: a header, then 500,000 rows of 64 bytes, best first. About 32 MB.

Step 3: play the best 500,000 with shuffles 2, 3, and 4

  1. The Python script splits the 500,000 rows into numbered ranges.
  2. Each cloud computer reads only its slice of top-500000. It needs only the strategy numbers from those rows.
  3. For each number it rebuilds the shopping list, plays nine games (three shuffles × three dummy opponents), and writes one 64-byte row with the totals from those nine games.
  4. Each computer appends its rows to its own file, in the same layout as step 1.

Step 4 and 5: add up and keep the best 20,000

  1. The reduce computer reads top-500000 and the new result files side by side. It checks the checksums and checks that every one of the 500,000 strategies has a new row.
  2. For each strategy it adds the shuffle-1 numbers and the shuffle-2-to-4 numbers.
  3. It ranks all 500,000 strategies by the totals and keeps the best 20,000.
  4. It writes reservoir: a header, then 20,000 rows of 124 bytes, best first. Each row holds the strategy number, the 15 numbers from shuffle 1, and the 15 numbers from shuffles 2 to 4. Keeping both sets lets anyone check the ranking later. About 2.5 MB.

Cleanup

  1. The Rust program reads both final files back and checks every header, checksum, row count, and the sort order.
  2. Only then does the Python script delete the range result files.
  3. Three files remain: top-500000, reservoir, and a small run report with timings, computer counts, and bytes read and written. The two result files hold no timing information, so the same run always produces the same bytes.

2. Build the first game matrix

The process in seven steps
  1. Take the best 50 strategies from the reservoir.
  2. Pair each strategy with every other strategy. That is 1,225 pairs. A strategy is not paired with itself, because that result is always 50%.
  3. For each pair, play 125 fixed shuffles. Play each shuffle twice, so each strategy goes first once. That is 250 games per pair and 306,250 games in total.
  4. Score each shuffle for the pair: 2 points for a win, 1 for a draw, 0 for a loss, added over the two games. So a strategy gets 0 to 4 points per shuffle against its partner. Keep every shuffle's points.
  5. Record what each strategy bought in every game. Later balance reports need this.
  6. Build the matrix from shuffles 1 to 75 only. A cell holds one strategy's average score against another, as a percentage. Shuffles 76 to 100 and 101 to 125 are kept for later checks and are not used here.
  7. Find the mix: a set of weights on the 50 strategies such that no strategy in the matrix scores better than 50% against a random draw from the mix. Save the matrix, the purchases, and the mix.
Plain language description

Goldfish scoring showed which strategies are fast on their own. It said nothing about how they do against each other. This step plays the 50 best Goldfish strategies head to head and writes down the results in a grid. The grid is the matrix. Row A, column B holds how well strategy A does against strategy B.

Going first is an advantage, so the game gives the first player a small health penalty. Even so, both seats can matter. That is why every shuffle is played twice with the seats swapped. The two results are added so seat order cancels out.

125 fixed shuffles per pair give a stable average. The shuffles are split into three groups: 75 for building the matrix, 25 for a later depth check, and 25 that stay untouched as independent evidence. This step plays all 125 but uses only the first 75.

The mix is the answer to: if you had to pick one of these 50 strategies at random, with what odds should you pick each one so that no strategy in the grid can beat your pick on average? Some strategies get weight zero. The mix is the starting point for the next step, which searches the reservoir for strategies that beat it.

Every game uses a fixed shuffle number, so any cell can be replayed and checked later. The 125 shuffle numbers for this step are fixed and are different from the four Goldfish shuffle numbers.

Implementation detail

Inputs

The Rust program reads the first 50 rows of reservoir from step 1. It needs only the 50 strategy numbers. It rebuilds each shopping list from its number, the same way as step 1.

Work unit

One work unit is one pair: 125 shuffles × 2 games = 250 games. There are 1,225 work units. The Rust program splits them across its cores. One core plays a pair from start to finish and keeps nothing in memory but the current game and its 125 result bytes.

The pair (A, B) gives both cells at once. B's points against A are 4 minus A's points against B. So the program never plays the reverse pair.

Result rows and result files

The pair result file has one row per pair: the two strategy numbers (4 bytes each), then 125 bytes, one per shuffle, holding the first strategy's points for that shuffle (0 to 4). Rows are in pair order: (1, 2), (1, 3), ... (49, 50). That is 133 bytes per row and about 163 KB for the whole file.

The purchase file has one row per pair and seat: the strategy number, the partner number, then one count per card in the kingdom for how many copies it bought across all 250 games, and one damage total per card family. About 200 KB.

Both files start with the same kind of header as step 1: what they cover, how many rows, and a checksum of the row bytes. Neither file holds timings.

The matrix and the mix

  1. The Rust program reads the pair file back and checks the checksum and the row count.
  2. For each cell it averages the first 75 shuffle scores and divides by 4. That gives a percentage from 0% to 100%. The diagonal is exactly 50%.
  3. It solves for the mix. This is a small linear program over 50 unknowns. It takes milliseconds. When more than one mix is equally good, the program chooses the one that spreads weight over the most strategies, then breaks any remaining tie by lower strategy number, so the answer is the same every run.
  4. It checks the answer: every weight is 0 or more, the weights add up to 1, and no strategy in the matrix scores more than 50% against the mix, within a fixed tiny tolerance.
  5. It writes matrix: a header, the 50 strategy numbers, the 50 × 50 percentages, and the 50 mix weights. About 12 KB.

Running locally

One Rust command does the whole step: read the reservoir, play the 1,225 pairs on all cores, write the two result files, build the matrix, solve the mix, verify, and write matrix. At the measured 10,000 to 12,000 games per second on a 10-core laptop, the 306,250 games take about 30 seconds. The whole step takes under a minute.

Running on Modal

This step is too small to split across computers. Splitting it would cost more in start-up and file transfer than it saves. So one cloud computer runs the whole step for one kingdom, the same command as the local run. On a 4-core cloud computer that is about 90 seconds.

Modal helps by running many kingdoms at the same time. Each kingdom's step 2 starts as soon as its reservoir file passes its checks. It does not wait for any other kingdom. The Python script only picks the computer, runs the command, and collects the three output files.

Cleanup and outputs

  1. The Rust program reads all three files back and checks headers, checksums, row counts, and that every matrix cell matches the pair file.
  2. Three files remain: pairs (all 125 shuffle results), purchases, and matrix. Plus the small run report with timings.
  3. The same inputs always give the same bytes, locally or on Modal.

3. Search the reservoir for strategies that beat the mix

The process in nine steps
  1. Take every reservoir strategy that is not in the matrix. At the start that is 19,950 candidates.
  2. Screen them. Play each candidate against the mix for 8 shuffles, two games per shuffle. The mix's strategies are shared out over the shuffles in proportion to their weights.
  3. Decide each candidate from its win rate and a confidence range. A candidate that clearly scores 51% or less is rejected. A candidate that clearly scores more than 51% goes to confirmation. Anything else plays more shuffles: 16, 32, 64, 128, 256, then 512. A candidate still unclear at 512 is marked unresolved and set aside.
  4. Confirm the candidates that passed screening with fresh shuffles: 400, then 800, 1,600, 3,200, and 6,400 while still unclear. The confidence requirement is stricter here, and it is shared across all candidates being confirmed at once, so confirming many at once is not easier than confirming one.
  5. Order the confirmed candidates by strength. Admit the strongest one to the matrix: play it against every matrix strategy for 125 shuffles, two games each, and add its row and column.
  6. Find the new mix from the bigger matrix.
  7. Retest the other confirmed candidates against the new mix with fresh shuffles. Admit the strongest one that still confirms, find the new mix again, and repeat until none are left.
  8. Run the search again from step 1 against the final mix of this round.
  9. Stop after two searches in a row that admit nothing. Save everything.
Plain language description

The matrix says which of the 50 strategies do well against each other, and the mix is the best way to pick among them. But the reservoir has 20,000 strategies. Maybe one of the other 19,950 beats the mix. This step looks for such a strategy, and when it finds one, it adds it to the matrix and tries again. It stops when it looks twice and finds nothing.

Playing against the mix means: for each shuffle, the candidate's opponent is one of the matrix strategies, chosen so that over all the shuffles the opponents appear in the same proportions as the mix weights. A strategy with weight 0 is never the opponent.

Screening is cheap and rough. It uses few shuffles and spends more only on candidates that are close to the line. Confirmation is expensive and strict. It uses fresh shuffles so a candidate cannot pass on a lucky screening result, and it demands a confidence range whose low end is above 51%. The 51% line, rather than 50%, means a candidate must beat the mix by a clear margin, not by noise.

Only one candidate is admitted at a time. Adding a strategy changes the mix, and a change in the mix can make the other confirmed candidates stop winning. So each one is tested again against the new mix before it gets its turn.

A candidate that stays unclear at the largest number of shuffles is recorded as unresolved. That is a result, not an error. Two clean searches in a row mean the reservoir has no strategy this process can confirm against the final mix. They do not prove that no such strategy exists outside the reservoir.

Implementation detail

Inputs and state

The Rust program reads reservoir from step 1 and matrix and pairs from step 2. Its working state is small: the list of matrix strategy numbers, the pair results (125 bytes per pair), the current mix weights, the candidate decisions so far, and which search and look it is on. After every look it writes this state to disk. If the run is stopped, the next run reads the state and continues from the last finished look. Nothing is replayed.

Shuffle numbers

Every shuffle number in this step is fixed by a formula from the search number, the stage (screen, confirm, retest, or admit), and the position in the sequence. Screening, confirmation, and retest use separate number ranges, so they never share a shuffle. The same candidate at the same look in the same search always plays the same games, locally or on Modal.

Sharing the mix out over shuffles

Each race builds one opponent schedule at its largest shuffle count. At schedule position k, the program chooses the positive-weight matrix strategy with the largest value of its normalized weight times k, minus its assignments so far. A tie goes to the lower strategy number. Every look uses a prefix of this schedule, so a later look plays only the new suffix. Every candidate in the same look faces the same opponent sequence.

Screening looks

  1. A look is one pass over all still-open candidates at one shuffle count. The first look plays 8 shuffles for every open candidate: 19,950 candidates × 8 shuffles × 2 games = 319,200 games.
  2. The program splits the candidates across its cores. A core takes a candidate number, rebuilds its shopping list, plays its games in shuffle order, and writes one byte per shuffle: the candidate's points, 0 to 4.
  3. After the look, the program computes each candidate's win rate and a confidence range that stays valid when it is checked again after more shuffles. Whole range at or below 51%: reject. Whole range above 51%: send to confirmation. Otherwise the candidate stays open for the next look.
  4. The next look doubles the shuffle count. It plays only the new shuffles and keeps the old bytes. Most candidates are rejected at 8 or 16 shuffles, so later looks are small.
  5. After the 512-shuffle look, any candidate still open is marked unresolved.

Confirmation looks

  1. The candidates that passed screening form one family. The confidence requirement for each is 5% divided by the family size, so the chance that any wrong candidate is confirmed stays at 5% for the whole family.
  2. The first look plays 400 fresh shuffles per candidate. Low end of the range above 51%: confirmed. High end at or below 51%: rejected. Otherwise double, up to 6,400. Still open at 6,400: unresolved.

Admission

  1. Confirmed candidates are ordered by: higher low end of the range, higher win rate, higher high end, better Goldfish rank, then lower strategy number.
  2. The first one is admitted. The program plays it against every matrix strategy for 125 shuffles, two games each, in the same layout as a step 2 pair, and appends the new pairs to the pair results. With 50 strategies in the matrix that is 12,500 games.
  3. It rebuilds the matrix percentages from shuffles 1 to 75 and solves for the new mix, the same way as step 2.
  4. The remaining confirmed candidates are retested against the new mix with fresh shuffles, using the confirmation rules and the same family requirement. The strongest one that still confirms is admitted next. This repeats until the confirmed list is empty.

Result files

Each completed look writes one binary file. The file starts with the new opponent seeds and strategy numbers for that suffix. It then has one fixed-size row for each candidate that entered the look, in reservoir rank order. A row holds the candidate number, rank, decision, cumulative mean and confidence bounds, the new point bytes, purchase counts, and family-damage totals. A resolved candidate does not appear in a later look from the same race.

Admission files hold the confirmed queue, the mix before and after admission, and all 125 point bytes and telemetry for each new matrix pair. A binary checkpoint names every completed file and the next transition. The final decisions file records every decision, admission, equilibrium, search result, and stop reason. Each file has a checksum and source identity. None of the scientific files hold timings.

Running locally

One Rust process runs the whole loop: screen, confirm, admit, solve, repeat, and stop. It loads the reservoir, matrix, and strategies once and uses one thread pool. Each look is one in-memory function call followed by one evidence commit. A first screening look is about 320,000 games. Because the process writes a checkpoint after every look, the same command can continue after a stop without replaying a completed look.

Running on Modal

One 16-core cloud computer runs one kingdom with the same Rust command as the local run. Python starts the process, commits the Volume after each Rust checkpoint signal, and returns the matching acknowledgement. Python does not inspect scores or choose the next transition. Different kingdoms can run at the same time.

If a computer is lost, Python starts the same command again. Rust checks every saved file, rebuilds its in-memory prefixes, and continues from the first unfinished look.

Cleanup and outputs

  1. The Rust verifier starts from the original reservoir and matrix, then checks every file, schedule, confidence bound, decision, admission, expanded matrix, and stopping rule.
  2. The outputs are the final pairs.hgm, purchases.hgm, and matrix.hgm files after any admission, every look and admission file, checkpoint.hpc, decisions.hpd, and a separate timing report.
  3. The same inputs always give the same scientific bytes, locally or on Modal.
